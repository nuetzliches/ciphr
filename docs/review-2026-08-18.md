## B9 is closed

The document calls this "the single most valuable mechanical check available here". It was done.

All three pinned known-answer vectors were reproduced byte-for-byte by OpenSSL's AES-256-GCM
(via Python `cryptography` 46.0.5), using the key, nonce, and AAD in the order the code supplies
them:

| Vector | Result |
|---|---|
| `WRAPPED_ROOT_KEY_HEX` | reproduced exactly |
| `WRAPPED_DEK_HEX` | reproduced exactly |
| `VALUE_CIPHERTEXT_HEX` | reproduced exactly |

Two further points, because a matching vector alone would not prove much:

- The value AAD was **rebuilt from the prose in `envelope.rs`**, not copied from `AAD_HEX`, and the
  result equals `AAD_HEX`. The documented format and the implemented format are the same format.
- Two negative controls passed: flipping one bit of the AAD changes the tag, and swapping the `aad`
  and `msg` arguments produces a different result — so the vectors are not accidentally insensitive
  to the ordering they are supposed to pin.

**B9 should be struck from the list of known imperfections.** The KATs now validate the primitive
and its plumbing, not only the format. What remains true is that they were *generated* by this code;
what is no longer true is that nothing independent confirms them.

## Findings

### 1. Invisible and confusable characters are accepted in paths — moderate, high confidence — **behoben, teilweise**

`ciphr-core/src/path.rs`, `inspect_segment`. Rejects `char::is_control()` (category Cc) and
`char::is_whitespace()` (the White_Space property). Format characters (category Cf) and
default-ignorable code points satisfy neither predicate and are accepted. NFC does not remove them.

Probed against the real API:

```
ACCEPTED  U+200B ZERO WIDTH SPACE    infra/db<ZWSP>     distinct from infra/db
ACCEPTED  U+00AD SOFT HYPHEN         infra/db<SHY>      distinct from infra/db
ACCEPTED  U+FEFF ZWNBSP              infra/db<ZWNBSP>   distinct from infra/db
ACCEPTED  U+2060 WORD JOINER         infra/db<WJ>       distinct from infra/db
ACCEPTED  U+202E RTL OVERRIDE        infra/<RLO>db      distinct from infra/db
ACCEPTED  U+0430 CYRILLIC SMALL A    infrа/db           distinct from infra/db
rejected  U+00A0 NO-BREAK SPACE      — "path contains whitespace"
```

U+00A0 is rejected only because it happens to carry White_Space. The others are the same trap and
pass. A second probe adds one more: `ﬁle/x` (U+FB01, the `fi` ligature) is accepted and is a
different secret from `file/x`, because that folding is NFKC and the design chose NFC — correctly, but
the consequence belongs in the same finding.

**This is not an authorization bypass.** Deny-by-default holds: `infra/**` does not match
`infra<ZWSP>/db`, confirmed in the same probe. What it is instead:

- **Operator deception.** An identity with `write` under any subtree can create a path that renders
  identically to another in `ciphr list`, in the audit trail, in a monitoring alert, and in a
  policy diff. Reviewing "which secrets exist" by eye stops being reliable.
- **U+202E is worse than the rest.** It reverses display order, so a stored path can render on a
  terminal as a path other than the one that was authorized and written.
- It contradicts the module's own stated reason for rejecting whitespace — "an invisible difference
  between two paths is a trap" — and it weakens claim A4: two spellings that a *human* cannot tell
  apart absolutely can exist.

**Resolution.** Segments are now drawn from an **allowlist** — letters and digits of any script,
plus `-`, `_` and `.` — instead of being filtered by a list of what to reject. That choice matters
more than the specific characters: a denylist has to be extended with every Unicode revision and a
gap in it is invisible until someone finds it, while an allowlist has no gap to find. Control
characters and whitespace keep their own errors, because those are the two a person types by
accident.

All six invisible characters from the probe are refused, with a regression test naming each.

**The confusable half is not fixed, and that is now a stated boundary rather than an omission.**
The Cyrillic `а` and the `ﬁ` ligature are *letters*, so any rule admitting non-ASCII names admits
them too; refusing them means either an ASCII-only path space or a script-mixing policy, and neither
belongs in v1. A test pins that they stay distinct paths, which is what keeps authorization sound.

One cost, recorded because it is a real trade: path segments could previously contain `%` and `[`,
and a store test used them to prove the prefix listing is a range scan rather than `LIKE` or `GLOB`.
Neither is a legal path character now. `_` is also a `LIKE` wildcard and still legal, so that guard
survives; the `GLOB` half of it does not, and the test says so instead of quietly covering less than
it claims.

### 2. Timing separates "this token identifier exists" from "it does not" — low, high confidence — **behoben**

`ciphr-store/src/tokens.rs`, `authenticate`. The module documentation claims:

> An unknown identifier, a wrong secret, an expired token, and a revoked token all produce the same
> outcome. Distinguishing them would confirm to whoever is probing that an identifier exists.

By return value that holds — all four are `Ok(None)`. By timing it does not. An unknown identifier
returns at the `self.token(...)` lookup, before the second query in `verifier_for`, before
`HMAC-SHA256`, and before the constant-time comparison. A known identifier does all three.

What an attacker gets: an oracle for valid token identifiers. The identifier is 48 bits, so remote
enumeration is not practical, and holding one does not help against the 256-bit secret. The finding
is that **the code is weaker than the property it states**, in the one module whose whole subject is
not leaking which failure occurred.

**Resolution.** Both paths now derive the verifier and run the same constant-time comparison, an
unknown identifier against a fixed stand-in. This **narrows** the difference rather than closing it:
the known-identifier path still performs one more database query. Equalising that would mean issuing
a query nobody needs, and what remains is a lookup on a 48-bit identifier that cannot be enumerated
remotely. Same class, still open and still not worth closing: `Token::parse` failing returns before
any database access at all.

Claim **C2 itself holds** — the verifier comparison is `subtle::ConstantTimeEq`, and expiry and
revocation are checked after it. That ordering is correct in the code.

### 3. `state.rs` and claim E1 describe an ordering the code does not implement — low, certain — **behoben**

`ciphr-server/src/state.rs`, module documentation, and `security-review.md` E1:

> **Reads** do the work, then audit with the real outcome, then respond.

`read_secret` calls `authorize_and_record` *before* `store.get`. Reads are record-then-work, exactly
like writes. The same wrong description appears again in the doc comment on `read_secret` itself.

The invariant that matters — no response leaves the process before a record is stored — is upheld,
and upheld more strongly than the comment claims. The risk runs the other way: **someone reading
that comment and making the code match it would move the record after the read and open exactly the
unlogged-read window the project exists to close.** In a fail-closed system a comment describing a
different design than the code is a live trap.

Related, and a real inconsistency rather than only a comment: the 404 branch writes a second entry
"so the trail does not imply a value was served", but the decryption-failure and non-UTF-8 branches
(`ApiError::Internal`, 500) do not. In those cases the trail says the read was allowed with status
200 for a value that was never served.

**Resolution.** The wording is corrected in `state.rs` and on `read_secret`, and the code is left
alone — recording first is the stronger property, and the danger was someone aligning the code to
the old sentence. The 500 branches now write the second entry too, through one `decrypt_to_text`
helper, so every outcome other than a served value is recorded as `not-served`. E1 in
`security-review.md` still carries the old wording and should be corrected there as well.

### 4. `/v1/list` records an allow that no rule produced — moderate, high confidence — **behoben**

`ciphr-server/src/api.rs`, `list_paths`. The prefix is never authorized. The handler records:

```rust
state.record_outcome(&caller, Action::List, Some(&prefix), &request, 200, None)?;
```

`record_outcome` with `reason: None` builds `Entry::allowed(action)` and attaches a principal, a
path, and a request — and **never a rule**, because there is no decision behind it.

Claim D4 names its own falsifier: "an allow with no rule attached — because an unattributable allow
makes the audit trail unable to say why." This is that entry.

Concretely: an authenticated identity holding no `list` capability anywhere can call
`/v1/list/infra`, be shown nothing, and leave behind an audit line reading *list, allowed, 200,
path=infra*. Two separate problems:

- The trail asserts an authorization that the evaluator never made.
- The trail does not record what was returned, so "who saw which secret names" cannot be answered
  from the audit alone — which is the question D8's per-result authorization is designed to make
  answerable. The comment says the disclosure is "bounded by the caller's policy, which the trail
  also records", but that requires cross-referencing a policy file that may have changed since.

**Resolution.** The entry now carries `results`, the number of paths the caller was shown, and the
listing is produced before it is recorded so that number can be truthful. Its presence is what marks
the entry as not being a decision — `rule` stays null there, and `allowed` means "the operation ran".
Authorizing the prefix was considered and rejected for the reason the plan already gives: `infra/**`
does not match `infra`, so a prefix check would refuse the listing to exactly the identity allowed to
read everything beneath it. The names themselves are not recorded, because an entry that grows with
the size of a listing is a way to make records unbounded.

### 5. Specificity ignores position and pattern breadth — design challenge — **dokumentiert**

`ciphr-core/src/pattern.rs`, `specificity()`; `ciphr-policy/src/evaluate.rs`.

Specificity is the count of literal segments. So `infra/**` and `*/*/*/DB_PASSWORD` are both
specificity 1, and both match `infra/host-a/service-b/DB_PASSWORD`. If they disagree about a
capability the result is `Tie`, which is a denial.

The behaviour is safe — it fails closed and it is deterministic. The objection is that it will
surprise: against the intended path scheme `infra/<host>/<service>/<KEY>`, a cross-cutting rule such
as "nobody reads `DB_PASSWORD` anywhere" is a natural thing to write and will tie with the broad
subtree grant on every path both match. The operator sees a denial whose recorded reason is `tie`,
and nothing in the policy file explains why two rules of visibly different breadth are equally
specific.

**Resolution: documented, semantics unchanged.** `docs/authorization.md` gains a worked example with
both spellings and what each records, and `decision_table.rs` pins it so the example stays true. The
semantics are left alone deliberately: the behaviour fails closed and is deterministic, and any
change here alters authorization outcomes in the crate still waiting for the external review. The
measured difference is in the *reason* — `tie` when the evaluator cannot tell, versus `not-granted`
when the narrow rule decides — which is also the argument for writing the exception with enough
literals to win outright.

Confirmed against the real matcher: `infra/**` and `*/*/*/DB_PASSWORD` both report `specificity() ==
1`, and both match `infra/host-a/service-b/DB_PASSWORD`.

### 6. The server discards every partial audit-device failure — moderate, certain — **behoben 2026-08-18**

`ciphr-audit/src/device.rs` states the contract:

> If one device of two fails, the record is written, the failure is reported in the outcome, and the
> caller decides what to do with it — surface it on the health endpoint, raise a metric. It is not
> silently swallowed: a second device that has been failing for a month is a second device that does
> not exist.

`AuditSink::record` honours its half: it returns `Written { seq, hash, failures }`. The only
production caller is `ciphr-server/src/state.rs:202`:

```rust
match sink.record(entry, now_millis()) {
    Ok(_written) => Ok(()),
    Err(_) => Err(ApiError::AuditUnavailable),
}
```

`failures` is dropped on the floor. `Written` has no other consumer anywhere in `crates/` outside a
doc example. And `/v1/health` reports `audit_devices` from `state.audit_devices()`, which is the
list of *configured* names captured once at startup — it says nothing about whether any of them
still works.

So the exact situation the module documentation names as the thing to prevent is the current
behaviour: a device failing every write for a month is invisible in the API, invisible in the health
endpoint, and invisible in the logs.

**Resolution, 2026-08-18.** `AppState` now keeps the per-device outcome of the most recent record
and `/v1/health` reports it as `{ name, accepting }`. `accepting` is `null` until the first record,
because "nothing written yet" and "the last write was accepted" are different states and a monitor
that conflates them reports a healthy device on a service that has never used it. The failure
*reason* is deliberately not reported: the route is unauthenticated and a device error message names
a path or a database. Two tests cover it, one of them driving a two-device sink where one device
refuses everything — the state this finding is about. **Finding 8 is untouched:** a gap left on the
lagging device is still, after the fact, indistinguishable from a deletion.

This also removes an operator's only means of monitoring the thing the module says to monitor.
Any deployment that runs two devices needs a health check for "is the second one still accepting
records", and **there is presently nothing for such a check to query.** Either the health endpoint
grows a per-device status, or that requirement cannot be met from outside the process.

### 7. A failed write can leave a torn line in the file device — moderate, high confidence — **behoben**

`ciphr-audit/src/file.rs`, `FileDevice::write`. The record is written with
`write_all(payload).and_then(write_all(b"\n")).and_then(flush).and_then(sync_data)`.

`write_all` is not atomic. It loops over `write`, and on a mid-way failure — `ENOSPC` being the
obvious one — part of the line is already on disk and the error surfaces afterwards. Two things
follow:

- `self.written += line_len` is skipped, so the in-memory size counter now under-reports the real
  file size, and rotation triggers late by exactly the lost amount, cumulatively.
- Nothing truncates the partial bytes. The next successful write appends to them, producing one line
  that is a fragment of one record followed by a whole one. Verification reports `Malformed` there,
  permanently, and there is no way to tell that apart from tampering.

The failure mode this hits is not exotic — it is the *designed* failure mode. `device.rs` names a
full audit volume as the expected operational failure, and fail-closed is supposed to turn it into an
outage rather than a protocol gap. It also turns it into an unverifiable file.

Fix: build `payload + "\n"` once, record the pre-write length, and on any error `set_len` back to it
before returning `Err`.

### 8. A transient failure on one device permanently breaks that device's chain, silently — moderate — **behoben**

Follows from the design plus finding 6, and neither part is wrong on its own.

`AuditSink::record` commits the chain when *at least one* device accepted the record. If the second
device rejected it, the chain advances anyway, and that device's file is now missing a sequence
number for good. Verifying it afterwards reports `SequenceGap` — or `PrevHashMismatch`, depending on
where it lands — which is the same signal the design defines as evidence of tampering.

`verify.rs` then prescribes the response:

> **Treat the gap as unknown, not as empty.** Every access between the break and the next verified
> record has to be assumed unlogged, and whatever those credentials could reach has to be treated as
> potentially read.

So a single transient `ENOSPC` on the secondary device commits whoever finds it months later to
credential rotation for an incident that never happened — and because of finding 6, nothing anywhere
records that the write failed benignly. The two findings compound: the evidence that would
distinguish "disk was briefly full" from "someone deleted a record" is generated by the sink and
then thrown away by its only caller.

**Resolution.** The devices that accepted a record now also record that another one refused it, as an
`audit-device-failed` entry naming the device. A gap found later is explainable from the trail itself
rather than by guessing — and guessing wrong meant treating a brief disk failure as an unlogged
access. The write is deliberately infallible and non-recursive: it goes through the sink once and
ignores the outcome, because turning a degraded trail into a failed request that had already
succeeded would be the worse trade. Refusing to commit unless every device accepted was rejected — it
makes adding a second device lower the availability of the first.

### 9. `::add-mask::` protects only byte-identical occurrences, and `set -x` defeats it — moderate, measured

Added after the rest of this document, from a run on a real Forgejo runner rather than a
simulation — the same binary and the same host-execution mode a deployment uses, via
`forgejo-runner exec -i -self-hosted`. It is a **what else**: nothing in `security-review.md` claims anything about
masking, which is why nothing there could have caught it.

`crates/ciphr-cli/src/formats.rs` states the premise correctly and the implementation follows it:

> A bare `curl | jq` therefore writes secrets into the job log the moment anyone adds `set -x` or a
> debug echo […] Masking is consequently part of the product rather than of the documentation.

The premise checks out. A runtime-fetched value with no mask registered appears in the log in full —
the runner does not mask anything it was not told about. And every ordinary case the format was
built for holds: same step, across steps through `$GITHUB_ENV`, multi-line values through the
heredoc form, a value embedded in a composed URL, and a value in the stderr of a failing command are
all redacted to `***`. The heredoc round-trip is byte-exact, verified by comparing SHA-256 digests
rather than by printing anything.

**What does not hold is the `set -x` case the module documentation names as its motivation.** The
runner matches masks as literal substrings. `set -x` does not print an argument verbatim — bash
re-quotes it — and two quoting forms change the bytes:

| Value contains | How xtrace renders it | Masked |
|---|---|---|
| alphanumerics only | verbatim | yes |
| a space, `$`, a backtick, a double quote, a backslash | `'value'` — content unchanged inside the quotes | yes |
| a newline | `$'line1\nline2'` | **yes**, see below |
| **a single quote** | `'part'\''part'` — extra bytes spliced into the middle | **no — printed in full** |
| **a tab** | `$'a\tb'` — the tab becomes the two characters `\t` | **no — printed in full** |

Measured, not reasoned: of eight values differing only in which character they contained, exactly
those two appeared in the log in cleartext, each on exactly one line, and each in a form that is a
mechanical and trivially reversible transformation of the real value.

The practical case is the single quote. A generated password drawn from a full punctuation alphabet
contains one about a third of the time at typical lengths; hex and base64 values never do. So this
is not theoretical for a store whose whole purpose is holding generated credentials, and the failure
is silent — the log shows a value that *looks* handled because every other line in the same job says
`***`.

**One thing that does hold, and by accident.** The newline case survives because masks are emitted
per line. `render_actions_env` justifies that with "runners match literal strings, so a value
containing a newline is never matched as a whole" — and the same property defeats bash's
`$'…\n…'` form, because each line's bytes still appear verbatim between the escapes. A correct
decision paying off twice, which is worth noting because it is the reason the multi-line case is not
a second entry in the table above.

What to do with it is a judgement, so both options rather than one:

- **State the limit.** The module documentation currently implies `set -x` is handled. It is handled
  for most values and not for all, and a security feature that is *usually* effective needs to say
  where it stops. This is the minimum.
- **Emit the transformed forms as additional masks.** For a value containing a single quote or a
  tab, also register the shell-quoted rendering. Cheap and it closes the practical case — but it is
  bash-specific, it would sit in a crate that otherwise makes no assumptions about the consumer's
  shell, and the next shell with a different tracing format reopens it. Defensible either way; the
  argument against is that it trades a stated limit for an unstated one.

What is **not** an adequate answer on its own is an operational rule against `set -x`. The module
documentation is right that the whole reason for the feature is that you cannot rely on nobody
adding it.

### 10. A CLI write while the server runs takes the service down until it is restarted — high operational impact, reproduced — **behoben**

Found while testing a deployment-side fetch helper against a running instance, not by reading.
Reproduced from a clean start:

```
1) server freshly restarted        GET /v1/list/infra -> 200
2) one `ciphr put` via the CLI, server still running
3) same request                    GET /v1/list/infra -> 503
4) same request again              GET /v1/list/infra -> 503
```

It does not recover. Every request afterwards is `503` until the server process is restarted.

**Mechanism.** The chain lives in memory, in `AuditSink`, and both processes have one. The server
resumes from the store's head at startup and holds its position from then on. A CLI write appends
records with *its* chain, so the store's head moves and the server does not know. The server's next
record carries a sequence number that is already taken, the SQLite device refuses it, no device
accepts it, and fail-closed does exactly what it promises: `AllDevicesFailed` → `503`, no response
served. And because the chain only advances on a committed record, the collision repeats for every
request that follows.

**Every part of this is a component behaving correctly.** The sequence number is unique because a
gap must be distinguishable from a deletion (E2). The request is refused because nothing may be
served unlogged. The chain does not advance because a record no device accepted must not consume a
number. The failure is in the assumption underneath all of them — that one process at a time writes
to a store — which nothing states and nothing enforces.

**Why this matters more than it looks.** The CLI is not an edge case here: `init`, `token issue`,
`import`, `destroy` and `rotate-master-key` have no endpoint *on purpose* (ADR-3), so the CLI is the
documented way to do them. Two of those are routine:

- `token issue` — every new repository or host identity needs one.
- `import` — the migration tool for an existing corpus, run once per service over dozens of values.
  Run against a live server, it takes the service down on the first write and keeps it down.

The security posture is not broken: nothing is served unlogged, which is the property that matters.
What breaks is availability, in a service whose unavailability blocks every deployment.

**What it is not.** Not SQLite locking — the write succeeds. Not a race that a retry fixes — the
state is permanently inconsistent until the process restarts and re-reads the head.

Options, none of them obviously right, which is why this is a finding and not a patch:

- **Re-read the head before committing**, so the server notices a moved chain and continues from it.
  Cheapest, and it makes concurrent writers work — but "works" here means two writers interleaving in
  one chain, and whether that is desirable is a design question, not an implementation one.
- **Refuse to start the CLI against a store a server holds**, with a lock file or the store itself.
  Honest and simple, and it makes `import` require a maintenance window — which for a migration is
  arguably correct and should then be *said*.
- **Say so and leave it.** The cheapest, and the worst: the failure is a total outage triggered by a
  documented, routine command.

The minimum, whichever is chosen, is that `docs/operations/cli.md` states it. Today nothing in
`docs/`, in the CLI, or in the store says that these two must not run at once.

**Resolution: the lock.** `ciphr-store::StoreLock`, taken by the server for the life of the process
and by the CLI for the duration of a command, both before the store is opened. A second writer is
refused with a message that says what to do. This adds no constraint that was not already there — a
restart was required after such a write anyway, because only a restart re-reads the head — it moves
the discovery from a permanent `503` to an error before the damage.

No new dependency: a file created with `create_new`, and liveness through `/proc`.

**Two things only the container found**, and both were wrong in the first version:

- Probing for `/proc` at runtime looked more portable than a `cfg`. On Windows `Path::new("/proc")`
  resolves against the current drive root and reported a directory, so the fallback never ran, every
  holder looked dead, and the lock was taken from a live process. Decided at compile time now.
- **A process id is not enough in a container**, where the server is always process 1. A lock left by
  a killed container names process 1, and the next container has one too — so a stale lock looked
  alive forever and nothing could start again after an unclean stop. The lock now records the
  holder's start time from `/proc/<pid>/stat` beside its id. Verified by killing a container and
  starting another: the stale lock was recognised and taken over with no manual step.

One transition cost, stated because it is real: a lock file written by a build that recorded only the
process id cannot be verified and has to be removed by hand once.

## What I did not find

Stated so the next reader knows what this pass does not clear:

- Nothing wrong in the envelope scheme, the key hierarchy, or the AAD construction. B1–B6 read as
  claimed, and the length prefix argument in B3 holds.
- The evaluator matches its four documented rules. Deny-by-default, most-specific-wins, tie-to-deny,
  and deterministic rule attribution are all in the code as described, and the sort before the
  capability check makes the reported rule independent of iteration order.
- A1 is a fact of the code: `normalize()` has exactly two callers, `SecretPath::parse` and
  `PathPattern::parse`. No second lower-casing, trimming, or NFC pass exists anywhere in `crates/`.
- B8 confirmed independently: `cargo tree -i rand -e normal` finds no non-dev dependency on `rand`,
  and the `ciphr-server` graph contains none.
- B10 confirmed: all seven crates carry `#![forbid(unsafe_code)]`.
- C4 confirmed by reading the decoder: no padding character is in the alphabet, `len % 4 == 1` is
  rejected, and the unused trailing bits of two- and three-character groups must be zero.
- C6 confirmed: `replace_seal` refuses a record whose root key identifier differs from the stored
  one.
- The reserved-prefix check is segment-aware — `system/config` is not caught by it.
- A2, A3, A5 confirmed by probe against the real API. Normalization is idempotent over combining
  marks, singleton decompositions, and the awkward NFC cases; NFC folds `e`+U+0301 and U+00E9 to one
  secret. Every documented rejection rule fires. The wildcard matrix is exactly as specified —
  `infra/**` does not match `infra`, `**` never matches zero segments, and `ab*`, `*ab`, `**/x`,
  `a/**/b` and `infra/***` are all refused.
- D7 confirmed: `deny_unknown_fields` on all four config structs, plus explicit refusals for
  duplicate policies, identities, patterns, capabilities, and policy references, and for a dangling
  reference. `from_toml` returns a `PolicySet` or nothing, so there is no half-loaded state to reach.
- E3 confirmed: `export` authorizes and records **inside** the per-path loop, and a single refusal
  aborts the whole call rather than returning a partial answer.
- E5 confirmed by reading `verify.rs`: an edit gives `HashMismatch`, a removal or reorder gives
  `PrevHashMismatch`, and a missing or renumbered record gives `SequenceGap` or `SequenceMismatch`.
  Verification re-serializes nothing, so the claim that a serializer change cannot invalidate an old
  chain holds.
- E2 confirmed: `Chain::encode` and `Chain::commit` are separate, and `AuditSink::record` returns
  before committing when every device failed, so a refused request consumes no sequence number.
- The `policy_file` fuzz target does check D4 — but at the `Decision` level, which is why it cannot
  see finding 4: the offending entry is built without consulting the evaluator at all.

## Fitness

`ciphr-crypto` is, on this reading, fit for a first production use holding real secrets. Nothing
found in it, and the one gap the document itself flagged as open is now closed against an
independent implementation.

`ciphr-core` and `ciphr-policy`: fit **with finding 1 addressed**. The path rules do not achieve
their own stated goal, and while the consequence is deception rather than bypass, a secret manager
whose listing cannot be trusted by eye undercuts the audit story it is sold on.

**The audit trail is the weakest part, and it is the part the product is sold on.** Findings 3, 4, 6,
7 and 8 all sit there. Individually each is small; together they mean that today, a ciphr instance
can lose its secondary audit device without anyone noticing (6), leave that device's chain
permanently unverifiable (7, 8), and offer no way to tell a disk failure from a deletion after the
fact (8). `ciphr-audit` itself is well built — the chain, the fail-closed sink, and the verifier are
sound, and the KAT pins the stored form properly. The gap is in the wiring between it and the
server, which is exactly the "second tier" the document chose not to make mandatory.

I would not run the two-device audit configuration until finding 6 is fixed. That configuration's
whole value is the second device, and there is currently no way to know whether it is working.

**This does not discharge the plan's precondition.** An external human reviewer is still required
before first production use. Findings 4, 5 and 8 are precisely the kind of judgement call where a
second person's disagreement is the point, and B10 — whether the dependency surface is acceptable —
is a question no amount of reading answers.
