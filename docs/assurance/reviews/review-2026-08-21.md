## Findings

Severity uses the two levels the deliverable asks to keep apart: **wrong** (the code or a claim is
incorrect) and **uneasy** (defensible, but a reader should decide deliberately).

### F1. Claim B6 is falsified: token secrets survive in unwiped heap buffers — wrong, certain

`ciphr-core/src/base64url.rs:65` (`decode`) allocates a `Vec` for the decoded bytes, and
`decode_into` (`base64url.rs:109`) allocates a second one via `decode` before copying into the
caller's buffer. Neither is zeroized. `Token::parse` (`ciphr-crypto/src/token.rs:156`) decodes the
secret half of every presented token through this path: the caller dutifully wipes its stack
array, while two heap copies of the 32-byte token secret are freed intact — **on every
authenticated request**. `Token::expose_text` (`token.rs:183`) has the same shape on the encode
side: `base64url::encode` returns a temporary `String` carrying the full secret, which is pushed
into the `Zeroizing<String>` and then dropped unwiped.

B6 claims "intermediate buffers are zeroized on both the success and the failure path" and names
`Token::parse` as a place to look. The hex path honours it — `from_hex` decodes in place into a
stack buffer and wipes it — the base64url path does not.

What an attacker gets: nothing remotely. This matters against memory disclosure, a core dump, or
swap — the exact adversaries the zeroization discipline exists for, per the threat model's "a
secret in a core dump or in swap" entry. The fix is small: wipe the intermediate `Vec`s in
`decode`/`decode_into` (or decode directly into the caller's buffer), and build `expose_text`
without the temporary. Until then, B6's wording is stronger than the code.

### F2. Claim D6 is falsified through the CLI: a real secret can shadow `sys/audit` — wrong, certain

The reserved-prefix refusal lives only in the HTTP layer (`ciphr-server/src/api.rs:881`,
`reject_reserved`, called from the write and delete handlers). Neither `ciphr-store`'s `put` nor
the CLI checks it: `ciphr put sys/audit` (`ciphr-cli/src/main.rs:415`) creates a real secret at
`sys/audit` without complaint. D6 says "a real secret can never shadow a virtual `sys/` path" and
names as its falsifier "a way to create `sys/audit` as a secret" — this is that way.

Consequence: one rule granting `read` on `sys/audit` — the natural grant for an auditor identity —
then authorizes two different things: reading the audit trail through `/v1/audit` and reading
whatever secret an operator planted at `sys/audit` through `/v1/secrets/sys/audit`. Creating the
shadow requires host CLI access, i.e. an operator, so this is not an escalation path; it is a
claim enforced at the wrong layer. The store is where the claim speaks, so the store (or the CLI,
or both) is where the refusal belongs.

### F3. "Nonce reuse is structurally impossible" is true one level down, not where it is stated — uneasy

The structural argument — one data key, one payload, one nonce — holds exactly at the DEK level,
and the property test pins it. But the **root key** performs AES-256-GCM with a fresh *random*
96-bit nonce for every DEK wrap (`envelope.rs:233`), one per version write, unbounded over the
life of a root key; the master key does the same per rewrap. Nonce collision there is not
structurally impossible, only negligibly probable, and NIST SP 800-38D bounds random-nonce use of
one key at 2^32 invocations. At this deployment's scale the margin is astronomically comfortable;
what is imprecise is the prose: `crypto.md` ("Nonce reuse becomes structurally impossible") and
the README state the absolute claim without naming the level it applies to. One sentence stating
the bound — and that a root key rotation resets the count — makes the claim exact. No code change
is needed at any plausible scale.

### F4. The corrective second audit entry is missing on the delete and export paths — uneasy, certain about the behaviour

The 2026-08-18 pass (finding 3) established the pattern: an allowed decision is recorded with
status 200 before the work, so any outcome other than success needs a second entry, and reads got
one for 404 and for decrypt/UTF-8 failures. Two paths still lack it at `v0.3.0`:

- **`delete_secret`** (`api.rs:400`): after `authorize_and_record`, the version resolution or the
  delete itself can fail (404 among others) and no second entry is written — unlike `write_secret`,
  which records `write-failed`. The trail then says an authorized delete happened at 200 when
  nothing was deleted.
- **`export`** (`api.rs:527`): entries are written per path *before* each read, and a failure —
  a missing path, a decrypt error — aborts the whole response after earlier entries are already
  committed. Every recorded "allowed, 200" for that request describes a value that never left the
  process. `read_secret` also skips the correction for store errors other than 404
  (`api.rs:298`), a narrower residue of the same shape.

The direction is conservative — the trail over-claims access, never under-claims — and E1's core
(no response before its record) holds everywhere I read. But `read_secret`'s own comment promises
"the trail never implies a value was served when none was", and on these paths it does. Either
extend the correction to delete and export, or scope the promise to reads.

### F5. The conceded denial of service is reachable without a credential — uneasy

Every request with a missing or invalid token writes an audit entry
(`api.rs:746` → `state.rs:454`), deliberately, so brute force is visible. Combined with
fail-closed auditing, this means an unauthenticated remote peer can grow the audit store and its
devices at line rate until the volume fills — at which point the service refuses everything. The
threat model concedes DoS by "filling the audit volume", but reads as if doing so takes a
credential or at least load; it does not. This is inside the stated boundary, so it is a
sharpening, not a defect: the threat model should say the fill is unauthenticated, and a
deployment note ("rate-limit unauthenticated 401s upstream, alert on audit growth") is the cheap
mitigation. ADR-16's deferral reasoning already contains the right thinking for exactly this
shape of endpoint.

### F6. The key-file check refuses world-readable, but not world-writable — uneasy

`check_not_world_readable` (`ciphr-crypto/src/seal.rs:261`) tests `mode & 0o004` only. A key file
at mode `0602` starts the process. World-*writable* key material is arguably worse than
world-readable: a local unprivileged user can replace the key — before `init`, that plants a key
the attacker knows; after it, it manufactures an unseal failure on the next restart. The check's
name is honest about its scope, and C9 as written is not falsified; the gap is that the rule
"unambiguously wrong file modes stop the process" plainly extends to `0o002`, and the same check
should refuse it. Group-writable is the judgement call; world-writable is not.

## Fitness statement

Asked, as the deliverable requires: are `ciphr-crypto`, `ciphr-policy`, and the reviewed parts of
`ciphr-core` fit for a first production use holding real secrets?

**Yes, qualified.** The envelope scheme, the seal, the token machinery, the path/pattern language,
and the evaluator are sound in design and implemented as documented; nothing found here weakens
confidentiality against the adversaries the threat model defends against, and the two falsified
claims are enforcement-layer and hygiene defects, not breaks. The qualifications:

1. **Fix F1 before relying on the zeroization story** (or weaken B6's wording until then). The
   crate's differentiator is that its discipline holds everywhere; today it holds everywhere
   except the hottest path.
2. **Fix F2 in the store**, where the claim speaks. One `starts_with` check.
3. F4 before the audit trail is used forensically for deletes or exports; F3, F5, F6 at the
   project's pace — they are precision and hardening, not exposure.

The judgement `security-review.md` reserves for a reviewer — whether the two designs that decide
every access are sound and implemented as described — I answer: they are, with the findings above
as the complete list of exceptions I could find. What this yes is worth, given who is saying it,
is the question the first section of this document exists to keep visible.
