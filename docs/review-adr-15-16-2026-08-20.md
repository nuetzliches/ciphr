# Design review — ADR-15 and ADR-16, 2026-08-20

**Reviewer:** Claude Opus 5, driven by the repository owner.

## Read this first

This is a **design** review of two ADRs whose status is *Proposed*. Nothing in either is implemented,
so there is no implementation to hold them to — except the code both of them cite as already doing
part of the work, which is where two of the findings below come from.

It is **not** the external review. `docs/security-review.md` asks for someone who did not write the
code, and every commit here from `a39f6ab` onward carries `Co-Authored-By: Claude Opus 5`. This pass
has the same blind spots as the designs it reads. Both ADRs name the external review as a
precondition; nothing here changes that line, and this document is not a step toward satisfying it.

**This document is a snapshot and is not extended.** Later findings go somewhere later.

## What holds up

Said first, because the findings are narrow and should not be mistaken for a verdict on the designs.

- **The oracle removal in ADR-16 is the right shape.** `202` for a match and a miss alike, with the
  lookup running identically either way, is the only version of this endpoint that does not describe
  the corpus to an anonymous caller. The rejected alternative — answer, but rate-limit — is named
  correctly as the same oracle, slowed down.
- **Property 3 of ADR-16 is genuinely load-bearing**, and the record says why in the strongest
  available terms: a mark that refused reads would be a remote kill switch keyed by the leaked value
  itself, operated by exactly the population the feature exists to hear from and not to trust. That
  argument is complete.
- **No outbound connection on alert.** An SMTP client or a webhook in the process holding the master
  key would be a new egress path out of the one container that should talk to nobody. `/v1/health`
  plus the audit trail plus a marker file leans on monitoring that section 17 already requires.
- **`freeze` recorded in the store, cleared only on the host, never on a timer.** Each of the three
  rejections around it — memory-held state, auto-unfreeze, a single untiered trigger — closes a real
  hole.
- **ADR-16 states what the blind index costs instead of arguing it away.** Duplicate-value
  visibility to A4 is new information, and the record says so before anyone asks.

## Findings

### F1 — A honeypot secret trips on every legitimate deploy, because the primary consumption pattern fetches values by prefix

**Severity: blocking for the design, not for the code.** ADR-15's placement story does not survive
contact with routes B and C.

ADR-15 requires the trigger to fire "on a value actually served" and enumerates what must *not* fire:
host operations (`dump`, `export` on the host), `list`, and `versions`. Plan section 22 adds the
honest caveat that "a honeypot secret is bait only while nobody depends on it", and says what
prevents that is the visibility rule — an operator can see the flag on the administrative path and
will therefore not build on the bait.

That reasoning assumes a consumer reads *named* paths. Since `0.2.0` the primary pattern is the
opposite: `ciphr-run --prefix`, `client.environment(prefix)` in `ciphr-sdk`, and the downstream
deploy helper all **list a prefix and then fetch the value of every path under it**. There is no
mistake for an operator to avoid. A honeypot secret placed anywhere under a prefix that any consumer
fetches is read — with a valid identity, through a value route, on every service start or deploy.
Which is precisely the signal the tier is meant to carry.

Two consequences the records should carry:

1. **A placement rule.** Bait must live outside every prefix any consumer fetches. Under an
   `infra/<host>/<service>/<KEY>` scheme that means bait belongs at a `<service>` level nobody
   deploys, and never beside the real secrets of a real service — which is the opposite of where the
   instinct puts it, because beside the real secrets is where an enumerator looks.
2. **That rule, not the visibility rule, is what makes the tier meaningful.** Once bait sits outside
   every fetched prefix, the only way to reach its value is to enumerate and then read something
   nothing needs — exactly the behaviour ADR-15 describes catching. The design still works; its
   stated safeguard is the wrong one.

For the record: ADR-15 is dated 2026-08-19, and ADR-14 and ADR-18 with the prefix-fetching routes
landed on 2026-08-20. The design predates the pattern that breaks it, which is the ordinary way this
happens.

### F2 — ADR-16's rate limit and its audit content both depend on a client address the server never obtains

**Severity: blocking for the build.** Two stated properties are undeliverable against today's code.

Plan section 23 says the per-IP bucket "keys on the connection address", and its audit section lists
what a report records: "the client address as the listener saw it". Both cite `request_context` in
`crates/ciphr-server/src/api.rs` approvingly, for the correct reason — it ignores `X-Forwarded-For`,
because a header a client controls is a header a client can lie in.

What the citation misses is the next line. `request_context` sets **`client_ip: None`**
unconditionally (`api.rs:729`), and nothing in the server extracts the peer address:
`axum::extract::ConnectInfo` does not appear anywhere. The doc comment above the function describes a
policy the function does not implement — a reverse proxy *would* show up as the client address, if
any address were taken at all.

Measured against a running deployment on 2026-08-20: two requests without a valid token produced two
audit records with `deny_reason: "unauthenticated"` and `user_agent: "curl/8.5.0"` — and
`client_ip: null`, `request_id: null`. The only request-origin field populated today is the one the
client chooses.

So, as written: the per-IP bucket has nothing to key on, and the one audit field that would make a
report actionable cannot be filled. The global budget — which section 23 already calls the real
defence behind a proxy — would be the *only* defence anywhere, including on a directly reachable
listener.

**This is buildable now and is not gated on the external review**, because it lives in `ciphr-server`
rather than in the crates the review must cover. It is a prerequisite for phase 9 rather than a
detail of it, and it is worth doing whether or not ADR-16 is ever accepted: an audit trail that
cannot say where an unauthenticated denial came from is thin in exactly the case it exists for.

### F3 — Both ADRs argue indistinguishability at the comparison and stop before the consequences

ADR-15, property 1: same format, same `401`, same body, "and no timing difference — recognition
happens on the existing code path with the existing constant-time comparison". ADR-16, property 1:
"The lookup runs identically either way, so there is nothing to measure."

Both statements are about the *decision*. Neither record says anything about what follows it, and in
both cases the consequence is asymmetric work on the request path:

- A honeypot hit writes a `tripwire` row, sets a flag on `/v1/health`, writes a marker file, and
  writes an audit entry with a distinct action. A plain invalid token writes one ordinary audit entry
  — measured: it does write one. The honeypot path is strictly more work, including a filesystem
  write, before the response is produced.
- A matched report sets `leaked_at` and writes a full audit entry naming the path; a miss does
  neither. `202` either way, at different cost.

The fix is a sentence in each record rather than a redesign: **the side effects happen after the
response is flushed**, or the path absorbs a fixed cost either way. Until one of those is written
down, the property both designs lead with is true of the comparison and false of the request.

### F4 — In a single-identity deployment, `disable-identity` is `freeze` under a milder name

ADR-15 prices the middle tier as "that identity's deploys fail until a token is reissued on the
host", which reads as bounded next to `freeze`.

That price is a function of how many consumers share the identity. A deployment with one machine
identity for every target — which is what a deploy runner shaped like the A3 story in plan section 22
looks like — loses *every* deploy when that identity's tokens are revoked. The two severe tiers then
differ only in whether running services can still fetch, and where nothing else holds a token they do
not differ at all.

Suggested wording: state the blast radius as *per identity*, and note that the per-service token
scoping route B makes worthwhile (ADR-14's closing consequence) is also what makes
`disable-identity` mean something other than `freeze`. The tiers are a granularity feature and they
inherit the granularity of the identity set.

### F5 — ADR-15 × ADR-16: a honeypot value in the wild is an anonymous, repeatable page

Each ADR is careful about its own half. ADR-15 property 4 permits an anonymous request to reach
`alert` and no further; ADR-16 lets anyone submit a candidate value. Compose them: whoever holds a
honeypot value can set `tripped` on the unauthenticated `/v1/health` at will, and `tripped` is what
monitoring turns into a page.

Formally this respects section 10 — `tripped` is a property of the process, not of the corpus — and
the cost is a page rather than availability, which is the trade ADR-15 chose deliberately. What is
missing is **repeatability**. Plan section 23 already makes `leaked_at` monotonic so that a repeated
report "changes nothing and costs one lookup"; nothing says the same about the tripwire.

Suggested resolution: **a honeypot trips at most once per bait until it is cleared on the host** —
the same latch `freeze` already has — and repeated reports of an already-tripped bait fall into the
aggregate entry that refusals use. Otherwise the mildest tier is the one an anonymous party can pull
on a schedule, and alert fatigue is how a tripwire stops being read.

### F6 — Fail-closed auditing turns a full volume into a honeypot distinguisher

Auditing is fail-closed: a request whose entry no device accepts is refused with `503`. A honeypot
token presented while the audit volume is full therefore yields `503` — and so does an ordinary
invalid token under the same condition, since it also writes an entry. Equal, so far.

The asymmetry arrives with the extra writes from F3. If the tripwire's row, its marker file, or its
distinct audit entry can fail independently of the ordinary entry, there is a state in which bait and
non-bait answer differently — and it is a state an adversary can help bring about by filling the
volume, which the threat model already names as a denial-of-service lever. ADR-15 should say which of
the tripwire's side effects are inside the fail-closed contract and which are best-effort, and that
the answer must not be observable on the value path.

### F7 — `leaked` on an `unclassified` secret leaves the operator without a next step, exactly where rotation is destructive

New since these ADRs were written. The rotation default became `unclassified` in the work dated
2026-08-20 (evening), on the reasoning that `rotatable` is a claim nobody may make by default.

ADR-16 rejects a truncated index and a Bloom filter because a false `leaked` mark on a `breaks-data`
secret "invites precisely the rotation that destroys data". That sentence now applies to a *true* mark
on an `unclassified` secret: the answer to a leak is a new version, and for an unclassified secret
nobody has yet said whether a new version is safe. The mark is a call to action the class cannot
answer.

This is an operations item rather than a design change: **on a `leaked` mark, classify before
rotating**, and `ciphr leak list` should show the rotation class beside the mark so the question is
asked where it arises. It belongs with the `docs/operations/` requirement ADR-15 already sets for
`freeze`.

### F8 — `leak reindex` is the one operation that can produce the state ADR-16 calls dangerous

ADR-16 names the half-indexed corpus as the dangerous state and puts the choice behind question 5 —
index unconditionally, or only where reporting is enabled. It then introduces `ciphr leak reindex`
for versions written before the migration, without saying what an interrupted run leaves behind.

Reindexing every version needs the master key and the store lock, which means the service is stopped.
It is the only bulk operation in the design with those three properties at once. An interrupted run
produces exactly the half-indexed corpus — arrived at by accident rather than by the configuration
choice question 5 is about — and the endpoint is designed not to be able to admit a miss.

Suggested: require the operation to be **resumable and to record its own progress**, and to report
what remains unindexed (`ciphr leak list --unindexed`, or a count on the administrative path). A
corpus that does not know which half of itself can match is worse than one that is not indexed at
all, because the endpoint's silence then means two different things.

### F9 — Two documentation claims go stale the moment either ADR is accepted (minor)

- `docs/threat-model.md`, the A1 row: "no anonymous endpoint except `/v1/health`". `POST /v1/report`
  is a second one, and the first that reaches the store. The row and section 10's rule should move in
  the same commit as the endpoint, under this repository's own rule about the changelog.
- Same file, the A5 paragraph: "whoever is root reads the master key from the service environment
  file". Since the `static_file` seal the key is a mounted file, and a deployment following current
  guidance has no key in its environment at all. The sentence is not wrong about A5 — it is wrong
  about where to look.

## Sequencing, given that the review gate is unmet

`docs/security-review.md` still reads "The review has **not** taken place", and both ADRs name it as a
precondition. Neither can be accepted. That is not the same as nothing being doable, and the split is
worth writing down before a later session re-derives it.

**Can be done now** — outside the reviewed crates, and without adding behaviour to the auth path:

- The `client_ip` plumbing from F2. `ciphr-server` only, and useful on its own merits.
- The false-positive enumeration ADR-15 requires before acceptance, which F1 says is currently
  missing its most important entry. A document, not code.
- The `freeze` operations document ADR-15 requires "before it has code".
- The placement rule from F1, in plan section 22.
- The wording fixes from F3 through F9.

**Cannot be done now:** anything that adds behaviour to the authentication path (ADR-15's core) or a
key derivation in `ciphr-crypto` (ADR-16's blind index). Both records already say so; F2 is the only
item that looked like it belonged to phase 9 and does not.

**On the dependency ADR-16 states** — "ADR-15 is built first" — F5 argues the composition needs a
decision *before* either is built, because the latch belongs to ADR-15 while the reason for it comes
from ADR-16. Deciding it late means deciding it twice.

## What this review did not check

- The cryptographic soundness of the blind index. `HMAC-SHA256` under a key derived the way
  `TokenPepper` derives one is a reasonable shape; whether the derivation is correct is a question for
  the review that has not happened.
- Whether the comparison in `tokens.rs` is in fact constant-time on the target, and whether
  `every_kind_of_invalid_token_looks_the_same` covers what its name claims. The name was read, not the
  body.
- Anything about how bait is planted in a real deployment. Plan section 22 puts that outside this
  repository, correctly.
